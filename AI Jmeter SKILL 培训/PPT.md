# 第 9 页：

### 标题：为什么测试计划先生成 JSON，再生成 JMX

**1. JMX 的树结构不直观**

* 每个 JMeter 节点后都必须跟一个 `hashTree`
* `hashTree` 用来表示该节点的子节点
* 没有子节点也必须写空的 `hashTree`

```xml
<TransactionController/>
<hashTree>
    <HTTPSamplerProxy/>
    <hashTree/>
</hashTree>
```

**2. AI 直接写 JMX 容易出现结构错误**

* 漏写 `hashTree`
* `hashTree` 层级错误
* Timer、Extractor 挂到错误节点
* 这些错误有时仍然是合法 XML，普通 XML 校验无法发现

**3. JSON 更容易表达测试计划结构**

```json
{
  "type": "transaction_controller",
  "children": [
    {
      "type": "http_sampler"
    }
  ]
}
```

只需要描述：

```text
Transaction Controller
└── HTTP Request
```

不需要处理 JMeter 的 `hashTree` 规则。

**4. Python 统一把 JSON 转成 JMX**

* AI 负责生成节点、顺序和父子关系
* Python 自动生成每个节点对应的 `hashTree`
* 同一套转换规则重复使用

```text
测试计划
   ↓
AI 生成 JSON
   ↓
Python 自动处理 hashTree
   ↓
JMX
```

**一句话总结：**

> 使用 JSON，是为了让 AI 只描述测试计划结构，把 JMX 的 `hashTree` 等格式规则交给 Python 统一处理。

# 第 10 页：编写SKILL的经验

1. 拆分
参照日常工作流的思路，把复杂的大 Skill 拆分成多个轻量化小 Skill，再按流程串联调用。
或者按步骤拆成多个独立的SKILL
2. 固化脚本
如果生成的内容是固化的（例如通过公式计算结果、已知元件属性生成Jmx脚本），建议固化成脚本而不是靠大模型对话去输出。
3. 验证
之前我的SKILL没有验证的步骤，但因为我用的模型可能比较注重自测和验证，所以即使脚本里有错误，AI也会自己改正错误 输出正确的版本。
这也导致我一直没有发现这个SKILL里存在一个bug。
但有些模型可能不会自己验证，所以我们最好自己添加验证的部分。



# Performance Testing Skill 分享稿

大家好，今天我主要想分享的是性能测试的 Skill。

首先，我们过去进行性能测试的流程是这样的：首先使用 Fiddler 对网页上的请求进行抓包，然后人工分析抓包内容，对请求进行参数化和关联，再组织脚本的结构，最后生成 JMeter 脚本。

现在我做的，就是把中间人工分析的这一步总结成了可以复用的 Skill。

首先简单介绍一下 JMeter。JMeter 是我们使用的性能测试工具之一，它的结构就像左边展示的这样，是一个纵向的树形结构。

这棵树本身其实就是性能测试脚本，它的本质是一个 JMX 文件。在执行的时候，JMeter 会按照这棵树从上到下执行，子节点也会跟随父节点一起生效。

大家可以看到，里面的一些节点包括 Thread Group（线程组）、Controller（事务控制器）、HTTP Request（HTTP Sampler），以及 HTTP Request 下面的一些提取器、请求头等子节点。

这些节点组合在一起，就形成了一个性能测试脚本。通过这个脚本，就可以模拟我们在网页上真实操作时发出的请求。

下面简单介绍一下，我们平时人工分析并生成脚本的时候，主要是在分析什么。

首先就是**参数化和关联**。

参数化比较简单，就是把参数的值写成变量的形式。

关联就是数据依赖，比如请求的返回值中提取 Case ID，然后传入下一个Open Case 的请求当中。

除此之外，人工分析中比较耗时的地方，还包括按照性能测试的目的调整脚本结构，以及针对不同的站点进行特殊处理。

可以看一下第一个例子。

对于 Login → Open Home → Add Case 这个流程来说，我们在页面上操作的肯定就是这个顺序，做性能测试的话很多时候就是让这整个流程去循环运行或并发执行。
如果我们测试的目的是整个站点的性能，那么这个流程其实没有什么问题。

但是，如果我们只是想持续并发测试 Add Case，单独测试这个功能的压力，那么这样的流程就会导致一部分测试压力被分散到 Login 等其他请求上。

还有的时候，我们想实现多个用户在同一时间点击 Add Case 按钮，也就是单个请求的并发。按照这样的流程也比较难实现。


第二个比较复杂的问题，就是同一个功能在不同站点上可能会存在差别。

例如 Report 功能，它里面的参数在不同站点可能会不同，包括页面和业务逻辑也有可能不同。

最后就是人工处理比较容易出错。

比如参数值的大小写和命名格式，可能会出现前后关联不上的问题或者一些小问题，虽然这种问题很容易发现，但处理也会比较耗时间。

所以，我做的就是把这些需要人工分析的部分总结成了 Skill。

下面我们可以先简单看一下 Skill 的实际执行效果。

这个例子来自一个 WO 里面的需求，要求测试在 Case 里面添加 Person 和添加 Property 的过程中是否存在死锁。

首先，我说明了脚本具体的业务流程，它也可以自己去分析但是我们加上说明的话分析的就会快一点
然后我自己设计了一下这个脚本的结构，包括我想要的执行过程，以及一些并发数这种参数等，然后让它生成测试计划。

展开它的思考过程，可以看到正确调用了SKILL，也对Fiddler脚本进行了分析。因为我安装了superpower这个插件所以它自己会有一些验证的过程。

打开它生成的测试计划，可以看到，前面是本次测试的一些参数，这些参数是它从请求和我们的对话中总结出来的。

同时，它也对我们发给它的 Fiddler 请求进行了过滤和处理，去掉了加载资源之类的请求，只保留了比较重要的请求。

Fiddler 抓取出来的请求本身是平铺的，没有任何层级关系。现在，在这个测试计划里面，它已经给出了脚本的层级结构，以及参数化和关联关系。

比如需要在哪些请求下面提取参数、哪些请求之间存在关联关系，以及这些参数会在哪些后续请求中被使用，它都给出了相应的内容。

这样，我们就可以对测试计划进行人工审阅。当然了不看也是可以的，可以只关注最下面这些需要我们确认的内容。

比如确认某个参数是否正确、是否需要添加断言，以及这些参数的设置是否正确。

在review之后，如果发现它分析得不对，我们就可以把问题反馈给它，让它继续进行修改。

比如说我发现有一个请求录制错了，所以我单独把这个请求重新录制了一遍，然后把这个单独的请求发给它，告诉它需要替换之前的某一个请求。

之后，我又补充了测试账号的信息，并让它生成最终的测试脚本。

这边就是它最终生成的内容，包括一个 JMX 文件，JSON文件和用于输入测试账号的CSV文件。

JSON文件属于中间文件。介绍 Skill 结构的时候会再讲到，但是我们平时进行测试的时候不需要关注这个文件。

只需要把最终生成的 JMX 脚本放到 JMeter 性能测试工具里面运行就可以了。

刚才这个是一个稍微复杂一些的例子，因为它对整个脚本的结构以及关联关系都进行了比较大的调整。

但是有的时候，我们可能并不需要这么复杂的脚本，只是需要用接口来向系统里批量**添加数据**。

这种情况下，就可以像第二个例子这样：我在录制完请求之后直接发给它，让它生成性能测试脚本，并且非常明确地告诉它参数应该通过什么方式取值，以及整个脚本应该采用什么样的结构。

我们描述得越清楚，它需要分析的内容也就越少。这样，它生成脚本也会越快。

所以Skill 相对于固定的程序来说会更加灵活一些。

我们希望它处理得复杂一些的时候，就可以让它比较完整地分析和构造整个脚本；而当我们的需求比较简单的时候，它也可以比较快速地给出最终的脚本，不需要浪费太多时间。

下面介绍一下这个SKILL的结构。
和刚刚演示的一样，它包含两个阶段，第一个阶段会加载两个reference文件，读取相关规则来将请求转换为文字版的测试计划。
第二阶段先将测试计划中的结构树转换为JSON文件，然后再通过python程序转换为JMX也就是XML文件。最后对生成的文件进行校验。

首先看下这个SKILL主文件的内容，它在两个阶段从reference文件夹读取4个单独的规则文件。为什么不把这些文件直接写进SKILL，是因为SKILL文件太长的话会影响生成效果，因为它要读取的细节太多了。
这样拆分出来就可以按需读取。这个主文件只需要控制整个流程的进行。

第一阶段加载的这两个规则文件，首先看这个计划规则文件。它的主要作用就是生成测试计划树，这个过程包含要过滤掉不需要的请求、分析测试目的。
第二个参数规则文件的作用是
